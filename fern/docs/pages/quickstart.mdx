## 1. Configure an approved Enterprise key

Access is provisioned through the MIS Enterprise release process. There is no self-service key-issuance endpoint in this contract.

## 2. Sign and send a request

Every Enterprise request is signed with `saferx-hmac-sha256-v1`. Send these headers:

| Header | Purpose |
|---|---|
| `X-SafeRx-API-Key` | Enterprise key identifier and signing secret input |
| `X-SafeRx-Timestamp` | UTC timestamp with an explicit offset |
| `X-SafeRx-Nonce` | One-use replay protection value |
| `X-SafeRx-Signature` | Base64url HMAC-SHA256 signature |

The signed canonical message is the uppercase method, escaped path, sorted query, lowercase SHA-256 body digest, timestamp, and nonce joined by newlines. The SDK clients implement this exactly. Never place credentials in source control or logs.


The generated SDK is the safest starting point:

```python
from saferx_pharma import SafeRxClient

client = SafeRxClient(
    base_url="https://saferx.online/api/enterprise/v1",
    api_key="YOUR_ENTERPRISE_KEY",
)

result = client.enterprise_safety_check(
    body={
        "locale": "en",
        "medications": [{"input_text": "Augmentin 1g"}],
        "requested_domains": ["ddi", "food_interactions"],
    },
    idempotency_key="integration-check-001",
)
```

## 3. Read the bounded result

A safety response contains `request_id`, `result_id`, `schema_version`, `surface`, `locale`, `summary`, `signals`, `domain_coverage`, `unavailable_domains`, `limitations`, `review`, `source_provenance`, and `display_obligations`. A client must preserve the review and limitation states; an empty signal list is not a universal safety guarantee.

## 4. Explore the registry

Use `enterprise_registry_autocomplete`, `enterprise_registry_search`,
`enterprise_registry_resolve`, and `enterprise_registry_product_detail` to
resolve and display registry-owned medication content. Registry requests need
the `registry_basic` entitlement.

## 5. Use OCR when the account is entitled

Prescription OCR is a native multipart Enterprise workflow, not a local eRx
OCR service. It requires the `ocr_prescription` entitlement and exposes upload,
status, events, medication resolution, safety, and review operations. Preserve
the returned `request_id`, `prescription_id`, review state, provenance, and
limitations in the integrating application.

The eRx integration uses the same public routes and does not share OCR files,
databases, or private service addresses with MIS.
