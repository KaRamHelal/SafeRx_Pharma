---
title: OCR prescription lifecycle
subtitle: Upload, track, read the outcome, and review a prescription image
---

Prescription OCR is an asynchronous workflow, not a single call. You upload an
image; SafeRx reads it, resolves every medicine line to a registry product, and
runs the safety check. When a line needs a person, the workflow waits in
`awaiting_review` until you submit decisions.

```text
enterprise_ocr_prescription_create          (upload, 202)
        |
        v  poll or subscribe
enterprise_ocr_prescription_read  <---  enterprise_ocr_prescription_events (SSE)
        |
        |-- status completed / failed  ->  read reason_code (below)
        |
        '-- status awaiting_review
                |
                v
        enterprise_ocr_prescription_review   (decisions -> safety check -> completed)
```

`enterprise_ocr_prescription_resolve` and `enterprise_ocr_prescription_safety`
return the same prescription object. Resolution and the safety check run inside
the workflow on their own; these two calls report that state and never run
either step again.

## 1. Upload

`enterprise_ocr_prescription_create` takes a `multipart/form-data` upload —
the image file plus optional flags (`pipeline_profile`, and which safety
domains to check via `include_ddi`/`include_allergy`/etc.).
Requires `Idempotency-Key`. Returns `202` immediately with a
`prescription_id` and initial `status` (`accepted` or `processing`) — the
image has not been processed yet.

<Note>
This is the one Enterprise operation with a `multipart/form-data` body. The
request signature covers the exact raw multipart bytes sent, the same rule
as every other content type — see [Authentication](/authentication/overview).
All three SDKs build this correctly; if you're hand-rolling requests, sign
the literal bytes you send, not a JSON re-encoding of the form fields.
</Note>

## 2. Track progress

Poll `enterprise_ocr_prescription_read` or subscribe to
`enterprise_ocr_prescription_events` (a Server-Sent Events stream) rather
than assuming a fixed processing time. The result carries `status`,
`transitions[]` (history of state changes), and `document_context`
(classification of the uploaded image itself).

| `status` | Meaning |
|---|---|
| `accepted`, `artifact_validating`, `queued`, `processing`, `ocr_running`, `resolving_medications`, `safety_running` | In progress. Keep polling |
| `awaiting_review` | A person must decide one or more lines. See [Prescription review](/concepts/prescription-review) |
| `safety_incomplete` | Review decisions were saved, but the safety check after them could not run. Post the review again |
| `completed`, `failed`, `cancelled`, `expired` | Terminal. Read `reason_code` |

Treat an unknown status as in progress.

`enterprise_ocr_prescription_events` returns a finite `text/event-stream` snapshot:
one `event: transition` frame per recorded transition, whose `data` is the same
object as an entry of `transitions[]`, followed by one `event: status` frame
(`request_id`, `prescription_id`, `status`, `review`); the stream then ends.
Reconnect, or poll `enterprise_ocr_prescription_read`, for later transitions. A
transition's `payload` is always `{}` today. Until a line has been resolved,
`educational_context.source_snapshot_id` is `unresolved`.

## 3. Read the outcome

A prescription read ends in exactly one stated outcome, carried by `status` and
`reason_code`. **An empty `candidate_medications` list is never the whole
answer** — always read `reason_code`.

| Outcome | `status` | `reason_code` | Review | Billed |
|---|---|---|---|---|
| Medicines read | `completed` or `awaiting_review` | `null` | per line | yes |
| The page is not a prescription or medication document | `completed` | `not_a_prescription` | no | no |
| A prescription with no readable medicine line | `completed` | `no_medications_read` | **required**: a person must check the image | no |
| The OCR provider failed; **nothing was read** | `failed` | `ocr_provider_unavailable` | n/a | no |
| A SafeRx-side failure after retries | `failed` | `ocr_capacity_unavailable` or `workflow_processing_failed` | n/a | no |
| The quota reservation lapsed | `expired` | `quota_reservation_expired` | n/a | no |
| The review was completed with lines nobody resolved | `completed` | `review_incomplete` | **required** | yes |

<Warning>
`ocr_provider_unavailable` means the image was **not read**. Never show it as "no
medicines on this prescription". Upload again later.
</Warning>

`document_context.medications_present` is `true` only when medicines were read.
Otherwise it is what the document classification reported, or `null`; it is
never inferred as `false` from an empty read.

## 4. The lines: `candidate_medications[]`

There is one entry per recognized medicine line, in document order. **No line is
dropped**: a line with no registry match stays, with `review_state: unresolved`
and its raw text.

| Field | Meaning |
|---|---|
| `raw_span` | The text of the line as read |
| `ocr_candidates[]` | Every distinct reading of the line, primary read first (`rank` 1), each with its script in `locale` (`en`, `ar`, `mixed`), the line's reading certainty in `confidence`, and in `agreeing_reads` how many reads produced it (3.3.0) |
| `winner` | The selected product (`null` when nothing was selected) |
| `alternatives[]` | Other products, each with a `selection_reason` (below) |
| `review_required` | This line needs a person |
| `review_state` | `resolved`, `pending`, `unresolved`, `reviewed` or `not_a_medicine` |
| `review_reason_codes` | Why the line needs a person. Empty when it does not |
| `informational_reason_codes` | How the product was chosen when that needs no review |
| `certainty` | The line's certainty as two parts: `reading` and `match` (3.3.0, below) |

### Two certainties: reading and match

Each line has two separate numbers. Do not mix them up.

- **`winner.confidence` is reading certainty**: how sure SafeRx is that the line
  was *read* as written. Each line is read twice and the two reads are compared
  field by field (name, dose, unit); the weakest field governs.

  | The two reads... | Reading certainty |
  |---|---|
  | agree on every field (or both left a field empty) | 1 |
  | differ in the name | 1 − (edit distance ÷ length), e.g. 0.73 for "hydroxyzine" vs "hydralazine" |
  | one read saw a field the other did not, or the line was read once | 0.5 |
  | differ in the dose or the unit | 0 |

  Below **0.9** the line always needs review (`ocr_reading_uncertain`). A dose
  the two reads disagree on is therefore always reviewed.
- **`winner.final_score` is the match**: how well the registry product matches
  what was read. It is an ordering score, not calibrated, and says nothing
  about whether the line was read correctly.

Use `review_required` to decide whether a person must look, not either number on
its own.

### `certainty`: both parts in full (3.3.0)

Each line carries `certainty`, with two parts that SafeRx never blends into one number.

```json
"certainty": {
  "reading": {"value": 1.0, "fields": {"name": 1.0, "dose": 1.0, "unit": 1.0}, "reads": 2},
  "match": {
    "basis": "exact_product",
    "evidence": {"name": "exact", "strength": "matched", "form": "inferred",
                 "route": "inferred", "salt": "absent", "release": "absent"}
  }
}
```

- **`reading`: was the line read as written?** It is the per-field breakdown behind
  `winner.confidence`, and `reads` is the number of reads compared (1 or 2).
- **`match`: how was the product chosen?** It is the same `MedicationMatch` that
  [medication resolution](/concepts/medication-identity) returns. The precision of each
  `basis` is measured and published there.
- **`agreeing_reads` on each reading** tells two readings apart. With two reads, 2 means
  both reads agreed on it, and 1 means it is one read's version against the other's.

A line resolves without review only when the reading is certain **and** its `basis`
needs no review. Your integration may apply a stricter rule. For example, it might
auto-accept only `reading.value == 1` with `match.basis == "exact_product"` and send
everything else to a pharmacist.

<Warning>
**What these numbers are not.**

- **The two reads are not independent proof.** Both are two preprocessings of one image,
  read by the same model family. Their agreement corroborates a reading; it does not prove
  it.
- **The 0.9 threshold is not yet measured.** It has not been checked against
  reviewer-confirmed prescriptions. SafeRx measures it from reviewer decisions as they
  accumulate, and will publish the result when the sample is large enough.
- **Stored lines may show `null`.** Lines stored before 3.3.0 report `null` for a part they
  do not have.
</Warning>

<Note>
Before 3.1.0, `winner.confidence` carried the match score. It is now reading
certainty, as documented; `final_score` is unchanged.
</Note>

### How a line is resolved

Every line is resolved by the same rules as `enterprise_registry_resolve`
([Medication identity](/concepts/medication-identity)), with each reading of
the line as evidence. The read dose is part of the evidence, so the selected
product can never contradict the dose that was read: a read dose no product
has is `strength_not_available`. In addition:

- the readings must agree — a second reading that names a different medicine,
  or selects a different product, withdraws the selection
  (`ocr_readings_disagree`);
- a line that touches both sides of a known look-alike pair (hydroxyzine /
  hydralazine, Celebrex / Celexa / Cerebyx, Lamictal / Lamisil, ...) is never
  selected (`lookalike_risk`);
- a read line never receives a policy selection: a bare name with several
  variants goes to a person rather than to a default variant.

When the medicine, salt, release type, strength, form and route are all certain
and only the brand is a choice, one brand is selected, the line does **not**
need review, and `informational_reason_codes` carries
`equivalent_product_selected`. The other brands are listed in `alternatives[]`
as `same_generic_name`. The same product in several pack sizes is one medicine
and carries no code.

### Line review reason codes

| Code | Meaning |
|---|---|
| `ocr_reading_uncertain` | Reading certainty below 0.9: the two reads disagree |
| `ocr_judge_override` | The AI judge disagreed with the registry search; a person decides |
| `ocr_line_unreadable` | Nothing legible was read on the line |
| `ocr_readings_disagree`, `lookalike_risk` | See above |
| `ambiguous_candidates`, `strength_not_available`, `form_not_available`, `route_not_available`, `salt_not_available`, `release_not_available`, `approximate_name_match` | No product could be selected from what was read; choose from `alternatives` |
| `unmapped_medication` | No registry candidate; enter a product or mark the line not a medicine |

New codes may be added: treat an unknown code as "needs a person".

### Alternatives

| `selection_reason` | Meaning |
|---|---|
| `same_generic_name` | Another product of the selected medicine (same ingredients), for example another brand |
| `ocr_alternative_match` | Another **possible reading** of the line: a different medicine whose name is close to what was read. It is never an equivalent of the selected product |

Never substitute an `ocr_alternative_match` without a person confirming it.

## 5. Safety check

When no line needs a person, the workflow runs the six-domain safety check
over the resolved lines and the prescription becomes `completed`. When a line
needs a person, the check waits for the review; see
[Prescription review](/concepts/prescription-review). The safety semantics are
those of [Safety results](/concepts/safety-results).

## Retrying

Only `enterprise_ocr_prescription_create` requires (and accepts) an
`Idempotency-Key` — retry the same upload with the same key rather than
re-uploading. A prescription that `failed` with `ocr_provider_unavailable` is
not retried automatically: upload it again later with a new key. Review
decisions are safe to post again after a `503`; read the prescription first to
confirm it has not already advanced.
