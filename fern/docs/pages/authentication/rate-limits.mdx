## Quota classes

Every metered operation draws from one of five daily classes. Each class is **one
shared allowance**: every operation in it draws from the same counter, and a quota error
names the class in `quota.metric`.

| Class (`quota.metric`) | Operations | Units per call |
|---|---|---|
| `drug_lookups` | `enterprise_registry_search`, `enterprise_registry_product_detail`, `enterprise_registry_resolve`, `enterprise_registry_ingredients`, `enterprise_allergy_substances` | 1 |
| `autocomplete` | `enterprise_registry_autocomplete` (separate, so typing never eats into your lookup budget) | 1 |
| `safety_boards` | `enterprise_safety_check`, `enterprise_erx_safety_check` (sharing one pool) and `enterprise_allergy_resolve`; `enterprise_safety_check_batch` is 1 **per evaluated item** (nothing for a failed item); reading a stored check (`enterprise_safety_check_read`) is 0 | 1 / 0 |
| `ocr_prescriptions` | `enterprise_ocr_prescription_create`; the read, events, resolve, review and safety calls that follow one upload draw 0 | 1 / 0 |
| `mcp_calls` | Every hosted MCP tool call (see [MCP Server](/ai-integration/mcp-server)); `initialize`, `tools/list` and other protocol requests draw 0 | 1 / 0 |

A call costs the units above whatever its size: a 25-result search or a ten-medication
safety check is still 1 (a batch is the one exception: it costs what its items would cost
one by one). `enterprise_allergy_families` and the metadata routes draw 0. A request SafeRx refuses (a `4xx` such as a validation error)
draws nothing.

## Plans

Every plan grants every capability: registry, safety checks, eRx, OCR and the hosted
MCP server. Plans differ only in daily volume and in the per-key request rate. Each
tier is at least as generous as the one below on every class. Registry lookups are also
protected against bulk copying (see [Bulk lookup protection](#bulk-lookup-protection)), so
pace bulk resolution by request count, not only by your per-minute rate.

| | Free | Starter | Growth | Scale | Custom |
|---|---|---|---|---|---|
| Price (USD) | 0 | 49 / month · 490 / year | 199 / month · 1,990 / year | 699 / month · 6,990 / year | contract, from 1,500 / month |
| `drug_lookups` / day | 180 | 2,500 | 10,000 | 50,000 | 150,000 |
| `autocomplete` / day | 1,200 | 10,000 | 50,000 | 200,000 | 250,000 |
| `safety_boards` / day | 180 | 1,000 | 5,000 | 25,000 | 60,000 |
| `ocr_prescriptions` / day | 30 | 100 | 500 | 2,500 | 10,000 |
| `mcp_calls` / day | 180 | 1,000 | 5,000 | 25,000 | 60,000 |
| Requests / minute per key | 60 | 60 | 240 | 600 | 600 |

`enterprise_free` is self-service. The paid plans are assigned by SafeRx. A plan can also
run for a fixed term, such as an annual term or a complimentary upgrade, and then revert
to another plan at its end date. The Partner Portal's billing page shows your plan, its
term, your allowances and your usage over the rolling 24 hours.

Daily quota is a rolling 24-hour window: each request stops counting 24 hours
after it was made, so an exhausted allowance recovers as earlier usage ages out
rather than at midnight. Overage is denied, not billed, on every plan: requests past
the allowance return `429` until usage falls back under it.

### Short-term ceiling on self-serve plans

Self-serve plans (Free and Trial) also have a short-term ceiling per API key in
addition to the daily quota: sustained high-rate use within an hour is throttled
even when daily allowance remains. Paid plans have no hourly ceiling and are
bounded only by their daily quota and their per-key rate. Spread batch work
over time, or move to a paid plan for sustained volume.

## Reading a quota error

A `429` (or a quota-exhausted `403`) carries `quota` in the problem
response: `metric` (which class), `limit`, `remaining`, `reset_at`, and
`window_seconds`. Use `reset_at` to schedule a retry rather than polling: it is
when your usage next falls below the limit.

The code is `quota.exceeded` for both ceilings. The short-term ceiling sets
`quota.window` to `"hour"` (`window_seconds: 3600`); the daily quota has
`window_seconds: 86400`. The problem also carries `retry_after` (seconds); a
quota `429` may not carry a `Retry-After` header, so use `retry_after` or
`quota.reset_at`.

### Bulk lookup protection

The registry is protected against being copied wholesale. A key that keeps sending more than
25 `enterprise_registry_resolve` requests a minute for several minutes is treated as
enumerating the registry and is temporarily restricted. While restricted, metered routes
answer `403` with code `subject_restricted` (type `access-denied`). The problem has no
`quota` member and no `Retry-After`. The restriction lifts on its own once the key's traffic
is back to normal, usually within minutes and at most about half an hour. Requests sent
during the restriction keep it in place.

A resolve request counts once however many items it carries. To resolve many medicines,
send up to 50 items per request and cache the `sfrx_id`s you get back; avoid many
one-item requests in a tight loop.

## Request size

Every Enterprise request is size-checked before anything is reserved or charged.

| Limit | Error |
|---|---|
| JSON request bodies up to 2 MiB | `413 request.body_too_large` |
| `enterprise_safety_check_batch` `items`: 100 | `422 request.collection_too_large` |
| `enterprise_safety_check` `medications`: 50 | `422 request.collection_too_large` |
| `enterprise_allergy_resolve` `items`: 50 | `422 request.collection_too_large` |
| `enterprise_registry_resolve` `items`: 50 | `422 request.collection_too_large` |

The problem `detail` names the field and the maximum. OCR uploads (multipart) are not
affected by the JSON limit; they may be up to 20 MiB. A body larger than the platform
accepts at all is refused with the same `413 request.body_too_large` problem.

## Retry-After and safe retries

Treat `429`, `502`, `503`, and `504` as typed, retryable outcomes and honor
the `Retry-After` header, or the seconds in the problem body, when present:
`retry_after` on a quota `429` (`quota.exceeded`), `retry_after_seconds` on a
rate-limit `429` (`rate-limit-exceeded`) — it reflects the server's actual state, not a
guess. All three SDKs already do this (bounded exponential backoff for
502/503/504, honoring `Retry-After` for 429 up to a 60-second sanity
ceiling).

Only retry a request marked `safe_to_retry: true` in its error response, or
a request that failed before any side effect occurred. Never retry a
side-effecting request with a *new* idempotency key hoping for a different
outcome — that creates a second logical operation.

## Idempotency

`enterprise_safety_check`, `enterprise_erx_safety_check`, and
`enterprise_ocr_prescription_create` require `Idempotency-Key`. The key
identifies the request together with its body:

| Retry | Result |
|---|---|
| Same key, same body, original completed | The original response, byte for byte, with the header `X-SafeRx-Idempotent-Replay: true`. Nothing runs again and nothing is charged again. |
| Same key, same body, original still running or lost before it completed | The request runs normally. |
| Same key, different body | `409` with code `quota.idempotency.conflict`. |
| Same key, original completed but its response was too large to store (over 256 KiB) | The work runs again, is not charged twice, and the response carries `X-SafeRx-Idempotent-Replay: re-executed`. |

A new key means a new logical operation; don't generate a fresh key on every
retry attempt. The official SDKs reuse the key across their retry loop.

Before 2.0.4 a same-key retry returned `503 trusted_accounting_finalization_unavailable`;
that was a server-side defect, fixed on 2026-10-21, not a client error.

## Pagination

`enterprise_registry_search` paginates via `cursor`/`limit` on the request
and `pagination.next_cursor`/`has_more` on the response. Stop paginating
when `has_more` is `false`; `next_cursor` is `null` at that point.
`enterprise_registry_autocomplete` does not paginate — it returns a single
bounded page, sized by `limit` (max 20).

## Request IDs

Every response and error carries a `request_id`. Include it when contacting
support about a specific request — it's the fastest way to locate what
happened server-side for that exact call.
